================================================================================
DAT-MOVIE — ESPECIFICAÇÃO MOBILE-FIRST PARA iOS
Guia completo de produto, design visual, componentes, botões, tamanhos e mínimos
================================================================================

Documento-base para transformar o Dat-Movie (hoje uma SPA desktop de catálogo
pessoal de séries) em um app mobile-first para iOS SEM perder a essência.

Este arquivo é autossuficiente: pode ser copiado para outro projeto e usado como
checklist de revisão. Onde houver número, ele é regra. Onde houver "mínimo", ele
é piso, não sugestão.

Versão do levantamento: 2026-11-16
Fonte analisada: repositório dat-movie (index.html, style.css, src/, docs/,
assets/BRAND_GUIDELINES.md).

================================================================================
PARTE 0 — COMO USAR ESTE DOCUMENTO
================================================================================

0.1 Este é um documento de REGRAS, não de marketing. Cada seção termina, quando
    faz sentido, em uma lista de regras numeradas (R-xx) para você citar na
    revisão do outro projeto ("isto viola R-07").

0.2 Prioridades quando duas regras colidem (nesta ordem):
    1) Acessibilidade e legibilidade (toque e texto nunca abaixo do mínimo).
    2) Integridade dos dados e regras de negócio (PARTE 12).
    3) Identidade visual (PARTE 4) — paleta, fontes, anatomia do card.
    4) Convenções de iOS (PARTE 3 e 13).
    5) Estética/preferência pessoal.

0.3 "Essência" (o que define o app): catálogo pessoal de séries, progresso
    honesto por temporada/episódio, curadoria por Tier (S+ a D), listas livres,
    descoberta sem nota pública, tema quente com acento areia. Se algo não serve
    a isso, é candidato a corte.

0.4 Nada neste documento autoriza "redesenhar". A identidade visual é ativo, não
    dívida. Mobile-first significa REORGANIZAR e ADAPTAR, não trocar a cara.


================================================================================
PARTE 1 — A ESSÊNCIA QUE NÃO PODE SER PERDIDA
================================================================================

1.1 O QUE É O PRODUTO
    Catálogo pessoal de séries de TV (com espaço para animes e animações) que
    junta três coisas que normalmente vivem em apps separados:
      (a) ACOMPANHAMENTO de progresso — em que temporada/episódio o usuário parou;
      (b) CURADORIA pessoal — status, Tier (S+ a D) e listas customizáveis;
      (c) DESCOBERTA — busca no TMDb, filtros avançados e recomendações na Home.
    Backend: Supabase (Auth + Postgres com RLS). APIs externas (TMDb/Fanart)
    SEMPRE via Edge Functions — nenhuma chave externa vai ao cliente.

1.2 ESCOPO REAL
    O catálogo é de TV. Filmes não fazem parte do catálogo nem da allow-list de
    API. Não expandir para filmes "de graça" durante a migração mobile.

1.3 O QUE O PRODUTO NÃO É (não introduzir no mobile)
    - Não é app de filmes.
    - Não é rede social (sem perfis públicos, comentários, notas públicas).
    - Não é tracker automático (progresso é manual).
    - Não é offline-first (cache melhora repetição, mas depende de rede).
    - Não tem backend próprio (Supabase + Edge Functions são o backend).

1.4 PRINCÍPIOS DE PRODUTO (contratos que sobrevivem a qualquer mudança)
    P1. PROGRESSO HONESTO. Sem total confiável, a barra fica VAZIA em vez de
        mentir 100%. O mapa de episódios por temporada (seasonEpisodesMap) manda
        sobre a coluna total_episodios.
    P2. SEM DUPLICATA. O mesmo tmdb_id não entra duas vezes no catálogo do mesmo
        usuário. O banco tem índice único parcial como última defesa.
    P3. CURADORIA, NÃO ALEATORIEDADE PURA. Recomendações ancoram no topo de
        popularidade e reservam cota menor para exploração (mix 70/30).
    P4. SEM NOTA PÚBLICA. A descoberta não mostra vote_average. A nota é pessoal
        (Tier).
    P5. TÍTULO LEGÍVEL. Filtros de qualidade escondem produções bloqueadas,
        idiomas fora de en/ja/ko, datas absurdas, cards sem arte e títulos
        predominantemente não latinos.
    P6. SEGURANÇA NO SERVIDOR. Chaves do TMDb/Fanart nunca vão ao navegador.
    P7. TIER É PESSOAL. Não vem do TMDb; é ranking do usuário.
    P8. LISTAS SÃO LIVRES. Um título pode estar em várias listas; nunca duas
        vezes na mesma. Listas de sistema não podem ser apagadas.

1.5 IDENTIDADE QUE NÃO SE NEGOCIA
    - Acento areia (#E5D8BF no escuro / #7A663B no claro) é a ÚNICA cor de marca.
    - Tema escuro é o padrão; claro é override de token.
    - Três famílias: Inter (corpo), Sora (títulos), IBM Plex Mono (dado técnico).
    - Anatomia única de card: pôster 2/3, título SOBRE a imagem, barra no corpo.
    - Barra de progresso é PREFERÊNCIA do usuário (esconde o corpo inteiro).
    - Sem "glow"/halo colorido: sombras são pretas e discretas.

R-01. Preserve paleta, fontes e anatomia do card. Não "modernize" a identidade.
R-02. Preserve os 4 status (assistindo, concluido, planejado, pausado) e os 7
      valores de Tier (S+, S, A, B, C, D, sem tier).
R-03. Preserve o mapa de temporadas como fonte do progresso.
R-04. Não exiba nota do TMDb em nenhuma tela de descoberta.
R-05. Não introduza login social, comentários ou feed público.


================================================================================
PARTE 2 — ESTRATÉGIA TÉCNICA PARA iOS (PWA x CAPACITOR x NATIVO)
================================================================================

2.1 PONTO DE PARTIDA
    O app é JavaScript puro (ES Modules) + Vite, HTML estático e CSS puro, sem
    framework de UI e sem roteador. Toda a lógica de negócio vive em src/lib/.
    Isso favorece REAPROVEITAR quase todo o domínio.

2.2 TRÊS CAMINHOS (do mais fiel ao mais custoso)

    CAMINHO A — PWA mobile-first (recomendado como FASE 1)
      - Mesma base de código, layout reescrito para mobile.
      - Instalável via Safari ("Adicionar à Tela de Início").
      - Exige: manifest.json, apple-touch-icon, meta tags de iOS, service worker,
        safe areas, tab bar inferior, sheets.
      - Prós: menor custo, domínio reaproveitado 100%, um só código.
      - Contras: sem App Store; haptics limitados; algumas APIs restritas.

    CAMINHO B — Capacitor (recomendado como FASE 2, para App Store)
      - Envelopa o MESMO build web em um shell iOS nativo.
      - Habilita: Haptics, StatusBar, SplashScreen, Keyboard, Share, Push.
      - Prós: publica na App Store reaproveitando o código da Fase 1.
      - Contras: build/assinatura Xcode, revisão da Apple, mais superfície.

    CAMINHO C — Nativo (SwiftUI) ou React Native (último recurso)
      - Só se o requisito for performance nativa ou widgets profundos.
      - Custo alto; risco alto de perder a essência na reescrita.
      - Se adotar: PORTAR o domínio (PARTE 12) com testes antes de redesenhar.

    RECOMENDAÇÃO: Fase 1 = PWA mobile-first; Fase 2 = Capacitor se precisar de
    App Store. Não comece pela Fase 2 nem pela C.

2.3 O QUE A MIGRAÇÃO MOBILE EXIGE DA BASE
    - Reorganizar layout desktop em layout vertical (sem toolbar horizontal).
    - Trocar navbar superior por TAB BAR inferior + top bar contextual.
    - Trocar modais largos por SHEETS (bottom sheets) e telas empilhadas.
    - Introduzir rotas reais (deep link por tela/lista/título).
    - Introduzir camada de instalação (manifest, ícone, splash, service worker).
    - Introduzir safe areas e tratamento de teclado.
    - Manter intocado: src/lib/ (domínio) e o contrato das Edge Functions.

R-06. Nenhuma chamada ao TMDb/Fanart fora das Edge Functions.
R-07. O domínio em src/lib/ deve ser portado com os mesmos testes, sem mudar
      fórmula de progresso, filtros, dedupe, score ou cache.
R-08. Se for PWA: manifest, apple-touch-icon, meta de status bar e service worker
      são obrigatórios (o app desktop de hoje não tem — isso muda aqui).

2.4 CSP E ORIGENS (atenção ao migrar)
    A CSP atual restringe origens: fontes do Google, Font Awesome no CDN, imagens
    de image.tmdb.org, placehold.co, flagcdn.com, assets.fanart.tv e conexões com
    *.supabase.co e pt.wikipedia.org.
    - Qualquer nova origem (CDN, analytics, push) exige atualizar a CSP.
    - O import map resolve @supabase/supabase-js e sortablejs por CDN. Em um
      bundler real (Capacitor/React Native), remova o import map e empacote.

PARTE 3 — FUNDAMENTOS DE PLATAFORMA iOS
================================================================================

3.1 VIEWPORT E ÁREA SEGURA (obrigatório)
    - Meta viewport DEVE incluir viewport-fit=cover:
        <meta name="viewport" content="width=device-width, initial-scale=1,
              viewport-fit=cover">
    - Use as variáveis de ambiente CSS para safe areas:
        env(safe-area-inset-top)
        env(safe-area-inset-right)
        env(safe-area-inset-bottom)
        env(safe-area-inset-left)
    - Top bar: padding-top = env(safe-area-inset-top) + altura interna.
    - Tab bar: padding-bottom = env(safe-area-inset-bottom) + altura interna.
    - Conteúdo rolável: padding-bottom para não ficar sob a tab bar e o home
      indicator.
    - A faixa do home indicator (aprox. 34pt em aparelhos com Face ID) é área
      "proibida" para controles: nada clicável encostado ali.

R-09. Nenhum controle essencial pode ficar sob a Dynamic Island/notch ou sob o
      home indicator.
R-10. Rolagem não pode "vazar" para trás (overscroll-behavior: contain) em
      sheets e rails horizontais.

3.2 BARRA DE STATUS
    - Decida o estilo: barra clara (conteúdo escuro) no tema claro e barra escura
      (conteúdo claro) no tema escuro.
    - PWA: <meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">
      combinado com safe-area-inset-top.
    - Capacitor: usar o plugin StatusBar e sincronizar com o tema (system/dark/light).

3.3 SEM HOVER — REGRA CENTRAL
    - iOS não tem hover confiável. TODO estado que dependia de hover no desktop
      precisa de equivalente em toque.
    - No card: no desktop o hover revela o nome. No mobile, o nome deve estar
      SEMPRE visível sobre a imagem (o overlay já existe) OU aparecer em um
      primeiro toque que não abre o item. Recomendado: nome sempre visível.
    - Nenhuma informação pode existir apenas em estado de hover.

R-11. Proibido depender de :hover para revelar informação essencial.
R-12. O nome do título no card fica sempre legível (sobre o gradiente preto).

3.4 TECLADO
    - Fonte de input >= 16px para evitar zoom automático do Safari ao focar.
    - Use inputmode e type corretos: type="email", inputmode="numeric",
      autocomplete apropriado, enterkeyhint="search"/"go"/"done".
    - Ao focar um campo, garanta que ele não fique sob o teclado:
      use visualViewport / scrollIntoView({ block: 'center' }).
    - Evite elementos position:fixed reagindo mal ao teclado; prefira layout com
      altura baseada em 100dvh (dynamic viewport height), não 100vh.
    - Em formulários de login, "Done"/"Go" deve submeter.

R-13. Todo input tem font-size >= 16px (16px é o piso anti-zoom; 17px é o ideal).
R-14. Nunca use 100vh para telas cheias; use 100dvh (ou svh/lvh quando couber).

3.5 SCROLL E MOMENTUM
    - Rolagem nativa com momentum: -webkit-overflow-scrolling: touch.
    - Rails horizontais com scroll-snap (manter a primitiva única de trilho).
    - Esconder a scrollbar visual sem desabilitar a rolagem.
    - Pull-to-refresh: só onde fizer sentido (ex.: Home). Não usar em telas com
      formulários, para não recarregar e perder estado.

3.6 GESTOS
    - Swipe da borda esquerda = voltar (comportamento do sistema; não sequestrar).
    - Swipe horizontal em rails = rolar o trilho.
    - Long press = menu de contexto opcional (ex.: card → abrir ficha, remover).
    - Swipe em linha de lista = ações destrutivas (com confirmação).
    - Nunca usar gesto como ÚNICO caminho para uma ação crítica (precisa de botão).

R-15. Toda ação acessível por gesto tem também um botão/menu equivalente.
R-16. Não sobrescrever o gesto de voltar da borda.

3.7 HAPTICS (Fase Capacitor)
    - Feedback tátil leve em: marcar episódio, concluir temporada, salvar,
      confirmar ação destrutiva, atingir limite de stepper.
    - Não usar haptics em rolagem, nem em cada toque de card.
    - PWA: navigator.vibrate não funciona no iOS — não contar com ele.

3.8 TEMA E COR
    - Manter 3 estados de tema: system | dark | light, com escuro como padrão.
    - Anti-flash: script inline no <head> lê localStorage.theme e escreve
      data-theme ANTES do CSS.
    - color-scheme acompanha o tema (scrollbar, selects e controles nativos).
    - Tela retina: usar imagens @2x/@3x; pôsteres do TMDb em w342 (card) e w500
      (detalhe) já bastam para telas móveis comuns; não baixar w780+ em grid.

R-17. Preserve o anti-flash de tema; sem ele o app "clareia" depois de abrir.
R-18. Não hardcode cores em componentes; consuma tokens (ver PARTE 4).

================================================================================
PARTE 5 — LAYOUT E NAVEGAÇÃO
================================================================================

5.1 MODELO DE NAVEGAÇÃO MOBILE
    - TAB BAR INFERIOR fixa (substitui a navbar superior de desktop).
    - TOP BAR contextual no topo (título da tela + ações), colada sob a safe area.
    - Telas empilhadas para detalhe (título), perfil, listas e configurações.
    - SHEETS para ações rápidas (seleção de listas, filtros, confirmação).

5.2 TAB BAR (regra de tamanho)
    - Altura visual: 49-56px + env(safe-area-inset-bottom).
    - 4 a 5 abas no máximo. Sugestão alinhada ao produto:
        Início · Catálogo · Próximos · Pesquisar · Perfil
      (as listas do usuário migram para dentro de Catálogo/Próximos, com um
      seletor de coleção, para não estourar o limite de abas).
    - Item ativo: cor de acento + rótulo; inativo: --text-muted.
    - Ícone 24-28px, rótulo >= 10-11px em Inter (nunca Sora).
    - Cada item com área de toque >= 44x44.
    - NÃO usar barra superior com abas horizontais roláveis no mobile.

5.3 TOP BAR
    - Altura interna: 44-56px + env(safe-area-inset-top).
    - Esquerda: voltar (quando empilhada) ou marca.
    - Centro: título da tela (Sora) — truncar com reticências.
    - Direita: 1-3 ações (buscar, filtros, mais). Ícones >= 44x44 de toque.
    - Fundo --bg-primary, sombra discreta ou separador por tom.

5.4 GRID DE CARDS
    - Desktop hoje: auto-fill, mínimo 160px, gap 12px (classe histórica grid-cols-8).
    - MOBILE (largura de iPhone ~390pt):
        2 colunas é o padrão do catálogo (card ~171px com padding 16 e gap 12).
        3 colunas só em modo compacto, com card >= 104px e texto ainda legível.
        1 coluna só para listas de "linha" (não para pôsteres).
    - Gap: 12px (manter a escala). Padding lateral: 16px.
    - A largura do card é conhecida pelo JS (contagem "quantos cabem"): ao mudar
      a medida, atualize CSS e JS juntos (mesmo contrato).

5.5 TRILHOS (RAILS) DA HOME
    - Primitiva única de rolagem horizontal (scroll-snap + máscara de fade nas
      bordas + scrollbar escondida).
    - O esqueleto de carregamento usa a MESMA primitiva (troca sem "pular").
    - Card do trilho difere do grid APENAS na largura; raio, borda, superfície,
      tipografia e barra são os mesmos.

5.6 SHEETS (substituem os modais largos de desktop)
    - Apresentação de baixo para cima, com "grabber" e arrastar para fechar.
    - Raio superior --radius (10px). Largura = 100% da tela.
    - Altura: até ~90dvh; conteúdo rola, cabeçalho fixo.
    - Backdrop escurecido (rgba(0,0,0,.5-.7)); tocar fora fecha (quando seguro).
    - Foco preso no sheet; Escape/gesto de voltar fecha.
    - Confirmações destrutivas: sheet pequeno e centrado ou alerta nativo.

5.7 BREAKPOINTS
    - Mobile-first: base = telas estreitas; adicione degraus só se necessário.
    - Sugestão: 0-430 (iPhone), 431-767 (phablet/landscape), 768+ (tablet/desktop).
    - NÃO reintroduzir o comportamento desktop dentro do app iOS; se houver
      versão web, tratar como build separado.

5.8 LARGURA DE LEITURA
    - Sinopse e textos longos: máximo ~65-75 caracteres por linha.
    - Painéis (roleta, afinidade, ano): caixa preenchida com largura limitada.

PARTE 12 — REGRAS DE NEGÓCIO QUE A UI MOBILE DEVE PRESERVAR
================================================================================
A UI é orquestração; a regra vive no domínio. Não duplicar regra na tela.

12.1 PROGRESSO
    - assistido = episodio + soma dos episódios das temporadas anteriores (mapa).
    - total = soma do seasonEpisodesMap, se > 0; senão total_episodios.
    - total <= 0 -> 0. Sem mapa e assistido >= total -> 0 (total não confiável).
    - pct = round(min(assistido, total) / total * 100).
    - O MAPA MANDA sobre total_episodios.

12.2 STATUS E TIER
    - Status: assistindo, concluido, planejado, pausado. Qualquer -> qualquer.
    - planejado é uma FILA separada: só aparece na aba Próximos; nas outras,
      excluído.
    - Tier: S+ > S > A > B > C > D > sem tier. S+ e S são "favoritos" na Home.
    - Tier é pessoal; nunca vem do TMDb.

12.3 FILTROS E ORDENAÇÃO
    - Filtros: lista, aba, tipo legado, busca textual, status, tier, década
      (e idade/ano fora do catalog.js).
    - Ordenação: nome, progresso, data, tier, temporada, ano.
    - Busca local tolerante a erro (normaliza acento, minúsculas, pontuação;
      distância de edição por tamanho do termo).

12.4 DEDUPLICAÇÃO
    - Com tmdb_id: compara só tmdb_id. Sem tmdb_id: nome + tipo + ano.
    - Banco: índice único parcial (user_id, tmdb_id) WHERE tmdb_id IS NOT NULL.
    - Listas: UNIQUE(item_id, list_id).
    - 23505 -> "Este título já existe no seu catálogo.".

12.5 LISTAS
    - N:N; lista de sistema não pode ser excluída.
    - "Próximos" e "Lista de Desejos" identificadas por nome; escondidas do
      seletor da página do título.
    - Falhas parciais toleradas (Promise.allSettled).

12.6 BUSCA E DESCOBERTA
    - Sem filtro + texto >= 2 -> search/tv. Com filtro -> discover/tv.
    - Página lógica de 40 itens (2 páginas do TMDb).
    - SEM NOTA: nenhum vote_average na UI.
    - Texto + filtros juntos (texto vira filtro local no modo discover).

12.7 QUALIDADE DE CONTEÚDO
    - Proibições duras: produção bloqueada; idioma só en/ja/ko (ausente passa).
    - Defeitos relaxáveis: título não latino, data absurda (>365 dias futuro),
      sem arte.

12.8 CACHE E FRESH
    - TTL 1h, máximo 200 entradas, persistência debounced 250ms, restauração até
      7 dias, invalidação por prefixo.
    - fresh: ignora leitura e regrava.

12.9 SESSÃO E SEGURANÇA
    - Auth por e-mail/senha; nome em user_metadata.full_name (sem tabela profiles).
    - Edge Functions com verify_jwt + checagem de usuário real.
    - Chaves externas só em secrets.

R-54. A UI não recalcula progresso/filtro/dedupe; usa o domínio.
R-55. Nenhuma tela mostra nota do TMDb.
R-56. Nenhum dado de um usuário visível para outro (cache por usuário no mobile).
R-57. Chaves externas nunca no cliente.
